## Effective product requirement

An opted-in target project must make the Johnny workflow the normal entry route for software
change work in both Codex and Claude Code without copying the complete governance library into the
target. The adoption path must separately expose four truths for each host:

1. whether the target's auto-loaded host instruction surface activates the installed skill;
2. whether a project-scoped host behavior gate is enforced, instruction-only or unavailable;
3. whether repository gates can reject invalid document topology and ticket-declared code
   responsibility violations before integration;
4. whether required same-lifetime implementer delegation was merely observed by the reviewer or
   independently proven by a host callback.

The system must never label an instruction as enforcement. A model may still ignore an activation
instruction; therefore document topology and code boundaries need executable admission checks.
Claude Code may additionally use a target-owned, project-scoped hook as a behavioral gate, but that
hook is not repository authority and must not depend on the plugin at target runtime. Codex must
remain `INSTRUCTION_ONLY` unless an equivalent installed interception surface is proven.
Conversely, a repository cannot prove a native subagent call from Git shape alone, so dispatch
must remain `REVIEWER_OBSERVED` unless the host exposes a non-forgeable callback/readback.

## Non-negotiable properties

1. No machine-global behavior change is installed implicitly. Adoption is scoped to one explicit
   target repository. It writes one delimited, target-owned activation block after approval and,
   only under separate owner approval on Claude Code, a self-contained target hook/config.
2. Removing the plugin must not delete or rewrite target project files. A remaining activation
   block must be harmless when the skill is unavailable.
3. A managed document create/revise/replace/archive candidate is rejected unless every selected
   direct parent through the declared root carries the matching revision/digest/lifecycle edge.
4. Code-boundary admission consumes a ticket-owned responsibility contract and language-specific
   strict/AST/source checks. File length, class count and naming alone are not responsibility proof.
5. Tickets assigned to a distinct implementation owner route through same-lifetime native
   delegation and one completion wait. No runner, receipt, descriptor or bridge is added.
6. Git metadata, branch names, author strings, prompts and caller-written evidence cannot prove
   that delegation occurred. Unsupported provenance is reported as `REVIEWER_OBSERVED` or
   `UNAVAILABLE`, never `HOST_PROVEN`.
7. Every rejection names the violated contract and produces no integration mutation.
8. Codex and Claude Code are both required supported hosts. Each has its own activation adapter,
   native-dispatch behavior test and installed qualification; success on one cannot stand in for
   the other or permit a dual-host release claim.
9. Claude project-hook adoption is separately approved, target-owned and self-contained. Disabled,
   stale or bypassed hooks cannot report `HOST_GATE_ENFORCED`; plugin removal leaves target files
   intact and introduces no target runtime import from the plugin.
10. Probabilistic host behavior uses a fixed five-session evidence set per host/scenario. At least
    four must take the intended route and all five must avoid forbidden effects; retry-until-green
    is not permitted.
11. Native-dispatch unavailability includes exactly one bounded cause: disabled feature, absent
    tool, unsupported profile, unsupported host version, denied permission or unknown.
12. Cluster closure produces readiness only. A single shared release ticket owns version bump,
    payload regeneration/repin, publication and fresh Codex/Claude installed readback.
