## Change record

| Field | Value |
| --- | --- |
| Old rule | Revision 03 defined opaque storage ownership and lifecycle results but no exact cross-process exclusion. A storage adapter could mistake lock competition for a generic storage failure or modify a stream concurrently. |
| New rule | Every admitted storage operation first obtains one exclusive lock bound to the exact opaque storage identity. Contention is the finite result `LOCK_CONTENDED`; it performs no codec read/write/delete, ledger lifecycle advancement, report generation, target mutation, or provider action. |
| Re-admission | After lock acquisition, the adapter re-reads and revalidates ledger ownership, expected revision, lifecycle and containment before touching the stream. A stale/revoked/moved ref cannot use an earlier pre-lock check. |
| Reuse constraint | No source imports the existing `file_lock.py` until it is represented by a delivered catalog card and selected through the reusable-module process. A future lock adapter may use only the selected public contract. |

## Non-negotiable properties

1. `LOCK_CONTENDED` is not `STORAGE_BOUNDARY_VIOLATION`, success, retry success, or a hidden timeout. It means the exact stream was not entered.
2. Lock ownership is metadata-only and exact-identity bound. No request, response, report, ledger, error, or telemetry record exposes a filesystem path, prompt, source text, credential, URI, or provider event.
3. A holder release occurs in a bounded `finally` path. A release/adapter failure never manufactures a completed result or a reduction claim.
4. Fixture and future process tests must prove that one competing operation sees `LOCK_CONTENDED` while the other operation alone owns the lifecycle change. They must retain complete failure evidence and clean their disposable root.
5. Ticket 06's pre-Revision-04 candidate is uncommitted evidence only and may not be integrated. Its missing lock contract is a requirement change, not an implementation correction.

## Classified file-lock capability authority

The owner additionally authorizes one upstream reusable-capability ticket: preserve the existing
blocking `ExclusiveFileLock` API and add a separately callable, finite classified nonblocking
acquisition surface. It may create only disposable test lock files and child processes below
test-created temporary roots. Its result is upstream evidence for a later telemetry adapter; it
does not authorize that adapter, a telemetry stream/ledger effect, provider/host invocation,
target-project mutation, cost claim, release, or deployment.

The capability ticket must distinguish the observed contention outcome from unrelated failures:
an independent Windows holder makes `msvcrt.LK_NBLCK` fail immediately with `errno.EACCES` on
this host. It may classify that exact acquisition outcome as contention only after its own lock
handle opened successfully. Every other open, acquisition, release, filesystem, or process
`OSError` remains an error and must not become `LOCK_CONTENDED`.

## Local lock-port adapter authority

The owner additionally authorizes one new, independently reviewable local
`TelemetryStorageLockPort` adapter ticket. It may select the delivered
`exclusive-file-lock` and `path-containment` capabilities, derive one opaque lock identity from
the exact four-coordinate stream identity `(storage_ref, project_id, stream_id,
ownership_ledger_ref)`, and create, hold and remove only dedicated lock files below the supplied
Johnny `telemetry` root. Its acquired token still retains the supplied storage revision. Its tests
may create disposable roots and use an independent child process to prove the
`LOCK_ACQUIRED`/`LOCK_CONTENDED` boundary.

This authority is deliberately narrower than Ticket 06: it does not create or read an ownership
ledger or telemetry stream, invoke the legacy JSONL codec, advance lifecycle or revision, map a
storage operation result, emit a report, access a provider or host, touch a target project, make
a cost claim, release software, or deploy. The later lock-bound storage adapter alone performs
the preliminary and under-lock ownership/lifecycle/containment re-admission from
`ADR-20260827-022`.

The selected lock adapter must preserve these finite meanings: an independent holder of the
same exact derived lock identity returns `LOCK_CONTENDED` with no token and no side effect;
acquisition returns a token carrying every coordinate of the supplied storage identity; release
accepts only that adapter instance's still-held original token and otherwise returns
`RELEASE_FAILED`. Non-contention filesystem failures remain sanitized adapter errors or finite
release failures; they are never relabeled as contention and never expose a filesystem path.

## Durable storage transaction authority — Revision 07

The owner authorizes a replacement for the currently missing controlled durable-storage boundary,
not a reactivation of Ticket 06's pre-lock candidate. A storage operation may act only on a
pre-existing, Johnny-owned ownership-ledger entry that exactly binds the opaque storage identity,
project, stream, lifecycle and revision. `APPEND`, `READ`, `VALIDATE`, `DETACH` and `UNINSTALL`
never create, register, repair or discover an entry from a caller-supplied root, path or identity.

`APPEND`, `DETACH` and `UNINSTALL` must use a durable, recoverable all-or-nothing transaction
for the stream bytes and ledger lifecycle/revision. The transaction journal is Johnny-owned,
internal and recovered under the exact stream lock before final admission; after a forced failure
or process interruption, the next admitted operation observes exactly the pre-operation state or
the post-operation state, never a mixed state. `READ` and `VALIDATE` must acquire the same lock,
recover any pending transaction and perform the same fresh ownership/lifecycle/revision/
containment admission before decoding the stream.

The future adapter must map malformed identity to `STORAGE_REF_INVALID`, missing or mismatched
ownership to `STORAGE_OWNERSHIP_MISMATCH`, inactive lifecycle to `STORAGE_CLOSED`, and owned
filesystem, codec, ledger, transaction or release failure to `STORAGE_BOUNDARY_VIOLATION`.
Contention remains `LOCK_CONTENDED` with no effect. A release failure overrides an otherwise
completed result. Direct use of `JsonlContextUsageStore.append` is prohibited in this controlled
path; strict record decoding may occur only behind the future adapter.
