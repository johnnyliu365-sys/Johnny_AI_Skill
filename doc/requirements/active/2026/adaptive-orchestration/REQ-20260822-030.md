## Change record

| Field | Value |
| --- | --- |
| Old rule | Executor choice lived partly in `doc/runbooks/dispatch-model-profile.md` and partly in unbound P8 prose. The P8 proposal hard-coded one provider's model names, had no PRD/CHG or Context binding, and could not distinguish a valid logical route from a host profile that is installed but not credential-capable. |
| New rule | A typed, provider-neutral table maps a semantic routing purpose and its exact ticket/decision evidence to an `ExecutorProfileRef`. A separate capability-profile registry resolves that reference to a provider, model and effort only when current capability evidence says it is available. Each implementation plan also binds a reviewer profile whose verified capability rank is not lower than the implementation profile. The resolver never embeds provider/model names, chooses a default, launches a host or issues a receipt. |
| Current approved profile intent | The human remains `ARCHITECTURE_OWNER`. Sol/high is selected only for project-initial review, requirement-change review that needs a complex-decision inventory, or the one-ticket reviewer uplift required when Terra implements. Terra/xhigh is the normal ticket-opening and review profile. Luna/xhigh is the normal implementation profile; a closed hard-ticket assessment may elevate that one ticket's implementation to Terra/xhigh, paired with Sol/high review. A Claude profile may express analogous tiers, but its installed CLI is not selectable until credential capability is separately proved. These are profile values, not resolver literals or authority grants. |
| Hard-ticket elevation | Elevation from Luna to Terra requires a ticket-bound `HardTicketAssessment`: the ticket cannot be further decomposed without breaking its observable closure, and the named evidence explains why its required reasoning exceeds the approved Luna capability. The reviewer then elevates from Terra to Sol for that ticket only. Missing, stale, cross-ticket or self-asserted assessment rejects the elevation. Model insufficiency after the bounded cycle returns `MODEL_CAPABILITY_INSUFFICIENT` to the architecture-owner route; it does not automatically select another implementer. |
| Owner override | An override may select only an available, registered profile and must carry an immutable owner record. It cannot invent a provider/model, suppress failed capability evidence or grant dispatch/implementation authority. |
| Rationale | Model identity is host-specific and changes over time; role authority, ticket-local elevation and the invariant that review strength never falls below implementation strength must not. Treating names in a runbook as executable policy lets a dispatcher silently use an unavailable or wrong executor. |
| Impact | New `doc/context/executor-routing/` draft and `modules/spec/executor-routing.md`; replacement ticket after SPEC approval; later revision of the dispatch profile into a versioned profile input; supersedure of unbound P8. No implementation source or host adapter changes are authorized by this requirement. |
| Acceptance source | `modules/spec/executor-routing.md` (owner-approved revision 01). |
