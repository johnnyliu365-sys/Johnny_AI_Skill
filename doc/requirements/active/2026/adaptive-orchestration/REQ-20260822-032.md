## Change record

| Field | Value |
| --- | --- |
| Old rule | Revision 07 treated effective task workspace/profile/rank readback as an absolute prerequisite to dispatch P8R. The current host lacks that readback, so an otherwise bounded POC resolver ticket was diverted into a new privileged host-gateway track solely to make dispatch possible. |
| New rule | Dispatch admission is profile-proportional. In the `POC` delivery stage, the evidence for the bounded ticket closure is the applicable document-mutation gate plus a reviewer-run, independently entered reverse mutation. Missing workspace-binding readback is recorded as the named known gap `KNOWN_GAP_WORKSPACE_BINDING_READBACK_UNAVAILABLE`; it is not converted into asserted workspace, profile, receipt-delivery, runner, or wake evidence. In `HIGH_ASSURANCE`, exact host task/workspace binding and effective profile/effort/rank readback remain mandatory before an implementation-source or Agent-control effect. |
| Profile decision | The owner and reviewer select and record the applicable POC or high-assurance path from risk evidence. A model name, task prompt, repository size, or desire to dispatch never selects the lower path. Existing non-negotiable security, authority, receipt, integration, and reviewer-only controls remain in force; a hard escalation still selects `HIGH_ASSURANCE`. |
| POC boundary | The POC path permits manual reviewer orchestration for the exact approved ticket. The reviewer must run the counter-mutation personally through a test path distinct from the implementer's evidence before accepting/integrating the candidate. The document-mutation gate remains the integration authority. This path makes no claim that an unarmed runner automatically delivered or woke a reviewer. |
| High-assurance boundary | The R07 host-gateway/workspace/profile binding remains a valid high-assurance closure. It may be resumed only from a replacement approved ticket that names `HIGH_ASSURANCE`; the known-gap record is never an alternative proof at that profile. |
| Rationale | AC-05 and AC-07 require ceremony to be proportional to risk. Treating an optional host capability as mandatory for every POC makes the control cost exceed its value and changes the project objective from P8R delivery into host-gateway construction. The corrective rule preserves real evidence and explicit limitations instead of fabricating readback. |
| Impact | Stop R07A as the P8R dispatch prerequisite and mark it `BLOCKED / REQUIREMENT_CHANGED`. Re-run the scoped Grill, Context, Specification, and ticket admission for P8R. No source, host, receipt, runner, workspace, task, provider, or Git effect is authorized by this requirement leaf. |
| Acceptance source | An owner-approved Revision 08 amendment to `modules/spec/adaptive-project-orchestration.md`, followed by a replacement P8R ticket. The amendment must define the finite known-gap record, POC reviewer counter-mutation evidence, and the high-assurance rejection of absent/mismatched workspace/profile readback. |

## Downstream constraints

1. The next SPEC must distinguish the POC delivery-stage exception from the existing
   `DeliveryProfile = COMPACT | STANDARD | HIGH_ASSURANCE` contract; it must not silently
   relabel one as the other or weaken a forced high-assurance classification.
2. The replacement P8R ticket must state its selected profile, the exact document-mutation
   admission point, reviewer-owned reverse mutation, the named known gap, and the prohibition
   against claiming automatic wake/delivery.
3. The revised R07 acceptance must prove that `HIGH_ASSURANCE` rejects absent, asserted,
   stale, mismatched, or lower-rank workspace/profile evidence. It may not use the POC known
   gap as success evidence.
4. Until the new SPEC and replacement ticket are approved, neither R07A nor P8R is dispatch
   authority. This change returns `REQUIREMENT_CHANGED`; it does not create a shortcut around
   ticket approval or integration review.
