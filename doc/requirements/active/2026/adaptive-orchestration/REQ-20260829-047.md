## Effective product rule

Remote Authority Commit remains a future capability, not an available writer. Any future attempt
to create a remote test ref, alter its protection, push a candidate, remove protection or delete
the isolated target must first pass through a separately qualified `HostExternalEffectGateway`.
The gateway is not the Router, plugin, CLI, environment, ordinary local file or user cache.

The only admissible authorization is an opaque, one-shot `ExternalEffectGrant` issued and consumed
inside a host boundary that the calling runtime cannot mint, alter, erase, substitute, replay or
use as a privileged effect credential. It binds one owner-approved immutable finite effect plan: credential-free remote
identity, declared read-only production ref, exact isolated target, qualified actor/role, exact
allowed effect set, expected observations/candidate identities, correlation and expiry. The gateway
atomically consumes the grant once before it begins the plan, revalidates every binding before each
plan-declared effect, and records only bounded,
credential-free evidence.

If a host cannot prove that independent boundary, it returns
`HOST_EXTERNAL_EFFECT_GRANT_UNAVAILABLE` before remote or provider effect. An ordinary file ACL,
environment literal, prompt declaration, receipt, Router record, plugin state or same-process
secret is not a substitute. Absence of this gateway never blocks the ordinary same-lifetime
`reviewer -> wait_agent -> review -> gate` implementation workflow, because that workflow has no
external-effect-grant requirement.

## Non-negotiable properties

1. The external-effect grant boundary is separate from dispatch. A missing bridge, receipt,
   descriptor, runner or host workspace readback must never block same-lifetime dispatch.
2. The gateway must be independently protected from the implementation/plugin/CLI identity and
   provide an atomic one-shot reserve/consume operation. A check followed by an ordinary local
   write, rename, delete or environment read is not proof.
3. Before each remote effect, the gateway itself verifies the immutable plan digest, caller role,
   repository identity, canonical full refs, actor/transport qualification, expiry, correlation and
   exact allowed operation. It never accepts a caller-selected path, actor, ref or effect list.
4. Gateway evidence contains bounded typed outcomes and opaque references only. Credentials,
   tokens, raw provider payloads, unrestricted command output, prompt text and grant material are
   never persisted in Router state, Context, telemetry, logs or review artifacts.
5. Cleanup may begin only after durable pre-cleanup evidence. Before removing protection or
   deleting an isolated ref, the gateway directly reads it and proves it still equals the
   gateway-owned expected SHA. Ref deletion must itself be atomically conditional on that expected
   SHA; a read followed by ordinary unconditioned deletion is not sufficient. Missing, changed,
   ambiguous or unpersisted evidence, or an unavailable conditional-delete primitive, is
   `RECOVERY_REQUIRED`: leave protection/ref untouched and prohibit later effects.
6. The gateway has no production-authority effect in this revision. It may be investigated only
   against a separately owner-authorized isolated target; production authority remains direct
   observation only.
7. A host/platform tuple is `UNAVAILABLE` unless capability evidence proves every property above.
   Unsupported hosts fail closed; there is no local fallback, synthetic receipt or reduced-PoC
   authorization.

## Boundary

This change authorizes no implementation or external effect. After exact Revision 14 approval, the
reviewer may open one evidence-only host-capability investigation ticket; that ticket must define
the candidate host tuple, actual independent principal/protection primitive, grant issue/consume
race model, tamper/replay/deletion adversarial probes, remote cleanup CAS semantics and bounded
evidence contract before any live remote scope is requested from the owner.
