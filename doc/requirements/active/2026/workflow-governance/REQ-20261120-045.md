## Boundaries

- **The plugin's boundary holds.** The plugin stays an external control plane: no target-project runtime, CI, hook, import, submodule or symlink dependency. The service is a separate component that the enterprise deploys; it is not part of any target project.
- **Wave 3 is not reversed.** Wave 3 retired a simulated runtime inside the plugin. The 1.0 service is a real, separately deployed component with its own security review.
- **The later SaaS phase is out of 1.0:** running it on our cloud, isolation between enterprises (multi-tenancy), billing and operations. Answer 1A means the same service carries over.
- **Prior art.** The `private-router-saas` POC (ticket `01-private-router-metadata-gate`, DONE) proved a boundary between a local thin plugin and a remote service, carrying only normalized metadata, with a fake transport. Its SPEC was archived by ticket 68 (`doc/archive/specs/2026/private-router-saas.md`). The 1.0 service gets a new SPEC that cites the archived one; the archived SPEC stays archived, as `requirement-lineage.md`'s SPEC archive rule requires.
- **The harness follows its own wave-4 rules.** The service's technology choice goes through REQ-044 T6 (a decision record with trade-offs and technical debt, approved by the owner) before its POC ends. Its module boundaries go through T5.
