## Change record

| Field | Value |
| --- | --- |
| Old rule | `main`, the checked-out branch, upstream configuration, `origin/<branch>`, a green CI run, a PR state, or a successful local merge could be read as integration authority. Several dispatch texts also read a live descriptor, receipt, host gateway, or runner as a universal prerequisite. None of those claims bind a versioned authority line or prove that the remote accepted the exact integrated SHA. |
| New rule | Every controlled project declares one versioned `project_authority_ref` and credential-free remote repository identity. A gate integrates only against a direct remote observation of that ref. Integration is complete only after the gate records the local integrated SHA, a non-force push targets that declared ref, and a subsequent direct remote readback returns the same SHA. `origin/<ref>` is diagnostic cache evidence only. |
| Integration states | `CANDIDATE`, `REVIEW_ACCEPTED`, `GATE_REJECTED`, `LOCAL_INTEGRATED`, `PUSH_UNCONFIRMED`, and `AUTHORITY_INTEGRATED` are distinct. A missing, failed, ambiguous, or mismatched post-push direct readback never becomes success; it is `PUSH_UNCONFIRMED` (or its more specific finite failure). |
| Collaboration rule | A project declares either `SINGLE_BRANCH` or `HIGH_COLLABORATION`; branch names are data, not policy. A single-branch project may declare `refs/heads/main`. High collaboration recommends development/staging/release authority lines and requires one ticket PR whose current head equals the candidate SHA and whose base equals the declared integration ref. The PR and CI are review/visibility evidence, not integration authority. |
| Enforcement rule | `HIGH_COLLABORATION` may claim enforcement only when provider readback proves both that ordinary UI actors cannot update or merge around the gate on the authority line and that a changed PR head invalidates prior approval. Missing proof is a named capability failure, never "best effort" enforcement. Applying or changing provider policy is a separately authorized external effect. |
| Synchronous-dispatch rule | Same-lifetime `reviewer → wait → review → gate` is not blocked by a runner, queue, receipt, descriptor, host gateway, workspace readback, or bridge capability. Cross-lifetime delivery alone consults `NOT_REQUIRED`, `AVAILABLE`, or `UNAVAILABLE`; `UNAVAILABLE` requires honest human relay rather than a fabricated wake. |

## Non-negotiable properties

1. `project_authority_ref` is a full `refs/heads/<name>` value validated at the boundary; it is
   never inferred from `main`, `origin/HEAD`, current checkout, a tag, an abbreviated ref, or a
   raw SHA. Remote identity contains no credential-bearing URL or Secret.
2. A direct remote observation binds repository identity, full ref, exact SHA, read method,
   normalized evidence digest, observer, and time. `origin/<ref>` may corroborate diagnostics but
   cannot admit, reject as current, or complete integration.
3. A remote move after the bound observation, a rejected push, successful-push-without-readback,
   or post-push SHA mismatch fails closed. No recovery may force-push, rewrite authority history,
   move an immutable release tag, or relabel local success as remote authority.
4. `HIGH_COLLABORATION` requires current PR head/base/approval evidence and proved provider
   enforcement. `SINGLE_BRANCH` does not incur that ceremony. Assurance level and collaboration
   topology remain separate axes; `POC`, `COMPACT`, `STANDARD`, and `HIGH_ASSURANCE` must not be
   silently collapsed into one enum.
5. Green CI, screenshots, provider UI claims, local remote-tracking state, raw provider payloads,
   and chat assertions are not authority. Durable artifacts contain only normalized metadata,
   identifiers, refs, SHAs, finite states, times, and evidence digests—never prompts, source
   trees, raw command output, tokens, cookies, authorization headers, or Secrets.
6. The correction of universal receipt/descriptor wording must preserve the receipt-bound,
   cross-lifetime supervision path. It must not build a queue, receipt issuer, host gateway, or
   polling mechanism merely to make synchronous dispatch appear available.
7. Before any source dispatch, the replacement specification and exact ticket must bind the
   authority-contract revision, profile/collaboration decision, finite errors, independent
   reviewer counter-mutation, and no-effect boundary. Existing tickets retain their historical
   authority only; none is silently expanded by this leaf.

## Acceptance source

A sealed `project-authority-integration` Context; an owner-approved specification with typed
authority, direct-read, PR/policy and integration-state contracts; independently reviewed tickets
that prove cache staleness, ref races, push/readback mismatch, stale PR approval, UI-bypass
capability, CI non-authority, credential rejection, and the bridge-unavailable synchronous path;
and a separate owner-authorized qualification for any live provider-policy or target-repository
mutation. The governance-reference release closes only after normal Level 1 publication and real
CLI verification.
